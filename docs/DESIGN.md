# 设计：Get It up 为什么长这样

这份文档解释「为什么」，不解释「怎么改代码」（那在 [INTERNALS.md](INTERNALS.md)）。

## 一句话

给原版台阶/楼梯的方块状态加一个属性 `giu_base`，记下「原来的底面被掰到了哪一面」，然后对**形状**套一个固定的 90° 旋转。状态里的 `facing` / `half` / `shape` / `type` 一个都不动。

几何只由纯函数反推：`形状 = R(giu_base, 原版形状)`。

## 为什么非得是方块属性

「竖着放的台阶」在效果上只是换个形状，看上去完全可以存在方块实体、区块附件之类的地方，但它必须能被这几样东西看见：

| 谁 | 需要的 |
|---|---|
| 碰撞与描边 | 每个 `getShape` 调用点，有些还不带位置 |
| 活塞、结构方块、`/fill`、调试棒 | 状态本身 |
| 存档与网络 | 状态本身 |
| 其它模组 | 状态本身 |

一旦做成「位置 → 朝向」的侧信道：活塞一推就丢，结构文件存不下来，没有位置的形状查询永远算错，而且还要自己写持久化。属性方案把这些全部白送，代价是**方块状态的 id 会变**（见最后一节）。

## 为什么只能在构造期注入

`Block` 的构造器里，`StateDefinition.Builder#create(...)` 一返回，状态表就冻结了；`registerDefaultState(stateDefinition.any())` 紧跟着就用上了它。之后往注册表里塞新状态会让全局状态 id 重排，而那个 id 已经写进了区块调色板、网络包和结构文件。

所以注入点是 `create` 的**最开头**，而且只能按类型判断（`instanceof SlabBlock` / `StairBlock`）—— 那一刻方块还没有注册 id。继承原版类的模组台阶/楼梯因此自动覆盖。

## `giu_base` 的语义

`giu_base` 是**原方块底面（底座）的外法线方向**，也就是材料贴着的那一面：

- `none`：原版形态，默认值。
- `north` / `south` / `east` / `west`：底座贴着那一面。

没有 `up` / `down`：竖起来的台阶一定贴在某个侧面上，`up`/`down` 只会与原版 `type` 冗余。默认值必须是 `none`，因为 `StateDefinition.any()` 取每个属性可选值的第 0 个，而默认状态紧接着就注册了。

`giu_base` 只记录「贴哪一面」，不记录「谁朝上」。后者由 `facing` / `half` / `type` 继续承担。

## 旋转是什么

绕「同时垂直于 DOWN 与 `giu_base`」的那条水平轴转 90°：

```
DOWN → giu_base → UP → 反方向 → DOWN        与 giu_base 垂直的两个水平方向不动
```

以 `giu_base=north` 为例，实际是绕 X 的 +90°：`(x, y, z) → (x, 1−z, y)`（以方块中心为原点）。形状绕方块中心旋转，`Shapes.rotate` 会把结果对齐到 1/16 网格。

**推论**：竖直楼梯的 `facing` 必须垂直于 `giu_base`。两者共轴时（比如 `giu_base=north, facing=north`）转出来的是原版形状的一个副本 —— 那是调试棒才会造出的组合，放置逻辑不产出。

## 台阶：六个槽位

| 槽位 | 写法一 | 写法二 |
|---|---|---|
| 下半 | `giu_base=none, type=bottom` | `giu_base=none, type=top` |
| 上半 | `giu_base=none, type=top` | `giu_base=none, type=bottom` |
| 南半（贴南墙） | `giu_base=north, type=bottom` | `giu_base=south, type=top` |
| 北半（贴北墙） | `giu_base=north, type=top` | `giu_base=south, type=bottom` |
| 西半（贴西墙） | `giu_base=east, type=bottom` | `giu_base=west, type=top` |
| 东半（贴东墙） | `giu_base=east, type=top` | `giu_base=west, type=bottom` |

同一个槽位有两种写法，差别只在**哪一面朝外**（也就是贴图朝向）。玩家放置永远产出 `type=bottom` 那一列，其余留给调试棒与命令。

`type=double` 在竖直状态下是一整块方块，分界线变成垂直的 —— 这就是「旋转过的双层台阶」。

## 楼梯：缺角的立方体

竖直楼梯 = 立方体缺掉「背对 `facing` 且背对 `giu_base`」的那个竖直角柱；剩下两个完整竖面正好是 `giu_base` 面与 `facing` 面。

楼梯的 `shape` 不止一种：

| shape | 缺口形状 |
|---|---|
| `straight` | 一个竖直角柱 |
| `inner` | 竖直角柱的上半格或下半格（补上另一半） |
| `outer` | 竖直角柱 + 相邻那格的一半 |

## 形状合并：谁的缺口被顶住，谁变

原版的判据是「邻居的 `facing` 与本块的 `facing` 垂直」。竖直之后这句话仍然成立，只是**垂直不等于同一个坐标系**：一个 `giu_base=none` 的普通楼梯，它的 `facing` 搬进竖直方块的坐标系后正好落在竖轴上，自然与本块水平的 `facing` 垂直。

所以规则是：

1. 把本块与邻居都搬到「本块的坐标系」里（用 `R⁻¹`）；
2. 邻居贴在本块的**缺口开放面**上 → 本块变 `inner`；
3. 邻居贴在本块的**实心高侧**（`facing` 那面）→ 本块变 `outer`；
4. **只有缺口被顶住的一方变**，另一方不动 —— 否则两块会同时改形状，丢掉视觉连接；
5. 两边都是 `giu_base=none` 时完全交回原版（本模组不碰纯原版场景）。

缺口有两个开放面：`facing` 的反面，以及半轴方向（`half=bottom` 时朝上、`half=top` 时朝下）。原版只探第一个，第二个是本模组补的。

左右之分（`_left` / `_right`）差的是缺口那一格里靠哪一边的那半格：先看邻居材料在缺口半边的面积偏往哪侧，偏不出来（对称）就看反面那一半并取反号。

## 贴图：几何转，图案不转

原版的 UV 钉在**世界**上：一张 8×16 的面取贴图的下半张。方块转成竖直后，几何转了贴图也跟着转，图案就躺倒了。

本模组因此按世界方向重新取样：

1. 旋转后法线为 `n` 的面，改用原模型里法线同为 `n` 的那张面的贴图；
2. 逐顶点按世界坐标重算 UV，默认**按位置裁切**（与原生一致，绝不变形）。

唯一的例外是「专门画的半高面板贴图」（`textures/block/*_slab_side`，1.21 里只有 `smooth_stone_slab_side` 一张）：它上下两半画的是两种东西，拿来裁必然在中间露一道接缝。这类贴图改用该方块自己身上那张**整张图**再裁，于是竖直单层台阶得到一整块带描边的面板。

`type=double` 时不替换：双层台阶的原版外观本来就是「两张半砖面叠起来 + 一道接缝」。

## 已知边界

- 竖直楼梯的踏步是竖直的：**纯装饰，不能走**，也不该被当成 bug 修。
- 状态 id 位移：装过本模组再卸载，旧存档里的方块会读成别的东西；`/fill` 与结构文件同理。
- 双端必须一致：客户端与服务端的状态 id 必须来自同一份配置。
- 靠近竖直楼梯的原版楼梯会被本模组改写 `shape`（这是形状合并的一部分）。
